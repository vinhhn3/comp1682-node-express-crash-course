Auth · steps 11 to 14

Two tokens, three answers

A password is checked once. After that the client carries a signed claim. Decode it, compare 401 with 403, then spend a refresh token twice and watch the second attempt fail.

0 The flow, before the pieces

Login writes a hash; refresh reads it back and replaces it. Play the arrows — each one carries the value written on it.

—

1 A JWT is three base64 parts

Header and payload are readable by anyone. The signature is the part that cannot be produced without the secret.

Log in to get a real token from this API. The concept server hides the sign-in call, so this page needs no token of its own.

Header

—

The algorithm. Not secret.

Payload

—

The claim: id, username, role, expiry. Readable. Never put a secret here.

Signature

—

HMACSHA256(header.payload, secret). Change one character of the payload and the server refuses the token. The client can read it; the client cannot forge it.

2 401 and 403 are different sentences

Both are refusals. Only one of them means “try logging in again”.

401 Unauthorized who are you? no token, expired token, bad signature
403 Forbidden I know who you are. You still may not.

The client's reaction differs: 401 → log in again; 403 → show an error, do not retry.

3 Rotation: one refresh token, one use

    
The access token is short and disposable. The refresh token is long, stored as a hash, and replaced on every use.


    

      

        the lifetimes
        

          
access · 15msent on every request

          
refresh · 7dsent only to rotate

        

        

          Stolen access token: 15 minutes of damage. Stolen refresh token: the server can revoke
          it, because a hash of it is in the user document.
        

      

      

        the rule
        

          Every refresh issues a new pair and replaces the stored hash. The old refresh
          token is now dead. Reusing it is a signal, not a convenience.
        

        

          A real system would also revoke the whole family when an old token is reused. That is
          the next step after this course.
        

      

    


    

      
    

    

      
Press it: login, refresh with the new token, then try the old one again.

    

  


  

    
! Where to keep the token

    

      

        
HttpOnly cookie

        
JavaScript cannot read it, so an XSS bug cannot exfiltrate it. The browser sends it automatically — which creates CSRF, so pair it with SameSite and a matching CORS origin.

      

      

        
localStorage / a header

        
Easy for a SPA and for curl, and what this course does. Any script on the page can read it, so one XSS bug is one stolen session. The 15-minute access token limits the damage.

      

    

    
The course returns both tokens in the JSON body so you can see them. A production login would put the refresh token in an HttpOnly cookie and keep only the access token in memory.
